The Challenge: Segment-Based Train Seat Booking System
Your task is to build a booking system for Sri Lanka's Colombo Fort–Badulla line — one of the world's most celebrated scenic train journeys — that lets a single reserved seat be booked independently for multiple, non-overlapping legs of the same journey.
Background: The line runs with 8 coaches: 3 reserved (every seat must be booked in advance) and 5 unreserved (first-come-first-served, no seat assignment). Reserved coaches are frequently under-occupied for long stretches of the route, since many passengers disembark partway through the journey, while the unreserved coaches are frequently overcrowded. Fares reflect this rigidity too: a passenger booking a reserved seat from, say, Colombo Fort to Kandy pays roughly double what a passenger takes for that same partial leg in an unreserved coach — the department's reasoning being that the fare has to cover the seat sitting empty for the rest of the journey (Kandy to Badulla), since under the current system that seat can't be resold once the train has departed. Leadership believes there's revenue being left on the table and cost being passed unfairly to some passengers, but hasn't committed to a fix.
Core Requirements:
Segment-based booking:
A seat vacated partway through the trip should become available again for someone else — for example, one passenger travels Colombo Fort → Kandy and another travels Kandy → Badulla on the same physical seat, each charged only for the distance they actually travel.
You decide how to model segment occupancy, calculate fares, and guarantee correctness when multiple people try to book overlapping or adjacent legs of the same seat at the same time — and should be ready to justify those choices.
Backend:
An API that manages stations, seats, and bookings, and correctly handles concurrent booking attempts on the same seat.
Frontend:
A way to select an origin and destination, see which seats are available for that specific leg, and book one.
Build it for real:
Build it as though it could genuinely be launched as a real application one day, not a disposable proof of concept. Treat the number of coaches, seats per coach, and stations as configurable rather than hardcoded, since the department could add coaches or extend the route in the future.
Running the project:
The project should run in one shot from a clean machine — a docker-compose up (or equivalent single-command setup) is recommended, with clear, step-by-step instructions for anything that can't be automated away.
